# Trusted #143 dispatch candidate — not deployed

This is a local candidate for a future independently reviewed default-branch workflow. It has not been pushed, merged, dispatched, tested with a real GitHub token, GitHub-hosted runner, Docker or a browser. The current main has a failing Runtime CI; this candidate does not change main or make that CI pass.

The `workflow_dispatch` entry accepts one independently reviewed full candidate SHA. Callers must provide only a SHA, never a secret: GitHub can retain dispatch inputs in event/UI metadata. The trusted jobs read the event file with a 64 KiB bound and emit only validated IDs/SHA. They use the SHA-pinned official `actions/checkout` to fetch only the trusted dispatch main SHA with `persist-credentials: false`; they never check out PR code. The checkout action itself receives the same `contents: read` token as the identity script, so its code is an additional trusted recipient; disabling credential persistence is not a claim that the action never receives it. Before running the script, a token-free step rejects mismatched action output, mismatched `git rev-parse HEAD`, a dirty/untracked tree, or git errors. These checks do not remove the need to trust the pinned action. `github.ref`, `github.workflow_sha`, `github.sha`, owner and actor are validated; GitHub permits a ref to be selected on dispatch, so a dispatch entry alone is insufficient. The trusted workflow and its full main SHA must be independently reviewed before dispatch. Read-only checks on 2026-11-15 found `main` reported `protected: false`, an empty repository ruleset list, and the collaborator list contained only owner `santa928` (admin/push). Default Actions workflow permissions were read and security auto-fixes were disabled. App installation write access was not established: the installation endpoint returned 401 requiring JWT and was not retried. The collaborator list alone does not exclude App credentials, tokens or concurrent owner automation; default workflow permission is not proof that every workflow is unable to request write permissions. The complete writer set and dispatch-race controls remain unverified. Do not treat main as protected. The workflow can be changed by a writer, so its own actor/ref/SHA checks alone do not independently authorize its code. Do not use a real token until the complete writer trust boundary and an independent exact-head / dispatch-race control have been verified. Any later main change makes the input/base check fail.

Four exact public GitHub API URLs (PR #356, main ref, latest Pages deployment, its statuses) get only the step-scoped GitHub token. The three fixed Pages assets never get that header. Redirects, untrusted URL arguments, oversized (>8 MiB) responses, invalid responses, timeout, changed identity, stale PR head/base, missing token and errors fail without printing payloads or token. The 15-second request+body deadline is independently enforced for asynchronous operations; it cannot interrupt synchronous event-loop blocking, but rejects when control returns after expiry. Actual public asset sizes and contents-only installation-token endpoint access remain to be verified in a permitted real runner.

Each identity job uses a pinned checkout action on a fresh GitHub-hosted VM; the observation job is separate with `permissions: {}`. The observation job uses a public HTTPS git fetch inside `env -i` with a fresh HOME, empty credential helpers, no hooks, no system/global config and no redirects, then verifies the fetched branch full SHA, source HEAD/tree and base ancestry. Its observation commands run in a minimal environment and do not receive an identity token. GitHub runner services and host processes may still hold ephemeral internal credentials: `{}` and `env -i` are not proof of a credential-free host or a sandbox against malicious reviewed candidate code. GitHub runner / public git behavior is untested; failure must stay failure. The exact observation candidate must be independently reviewed and tested, and after this workflow merges the candidate must be based on the new trusted main SHA before a result can be used.

The pre/observation/post outputs carry run, attempt, candidate SHA, base and b930 source. Admission rejects incomplete, skipped, cancelled, old-attempt, changed SHA or failed jobs and independently checks current public identity again. A canceled admission itself must be interpreted externally as not admitted. The check is point-in-time: recheck latest PR/main immediately before any later action and use expected-head safeguards when available. Observation outputs are not cryptographic attestations against malicious code in the candidate.

Node tests use only synthetic tokens, fake fetch and fake git. The suite and static shell/YAML validation do not establish production permissions, actual git behavior, fixed image availability, Pages→Local success or Issue #143 closure.
