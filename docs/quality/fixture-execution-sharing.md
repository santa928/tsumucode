# Manifest fixture execution sharing

The manifest fixture gate retains every Solution, Starter and authored fixture as a logical contract. `createCases` still produces the same identities and expectations. Only equivalent executions within one exercise are shared.

The two built TypeScript specialist suites retain all 92 authored inputs, including their raw diagnostic order, multiplicity and warning rejection. Their browser-side interaction helper and the manifest's Node helper cover different layers. Reducing the specialist inputs to 12 canaries and transferring 80 inputs to the manifest is deferred until the complete guarantees have an equivalent owner. Compiler source tests and React specialist suites also remain unchanged.

| Contract                   | Execution and oracle after grouping                                                                                                                                                                                                                                                      |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Runtime input              | Hash the runnable exercise descriptor (including runtime, rules, scenarios and viewports), workspace assets, exact file record and fault injection. A different value creates another execution. The gate supplies one runtime mapping to all members of a group.                        |
| Solution                   | Require exact `pass`, exact failed feedback rule IDs and any declared diagnostic codes.                                                                                                                                                                                                  |
| Starter                    | Require neither `pass` nor `system-error`, even if an authored member also checks a stricter status.                                                                                                                                                                                     |
| Authored fixture           | Apply its exact status, error diagnostic code set, failed rule IDs and expected unhandled rejection checks to the actual shared result. No oracle is replaced by another member's expectation.                                                                                           |
| Contradictory expectations | Keep separate executions. A coarse Starter cannot join two incompatible exact statuses. Diagnostic and failed rule conflicts also prevent sharing.                                                                                                                                       |
| Frozen release targets     | Emit the original course/lesson/exercise/case-kind/fixture/browser key, original exercise input digest and original source/fault digest for every logical member, after its own oracle passes. `readBrowserCoverage` still rejects missing, duplicate, extra or mismatched observations. |
| Isolation                  | Each group is one Playwright test with a fresh Page/Context and runner disposal. No result is cached between tests, exercises, runtimes or retries.                                                                                                                                      |
| Selection                  | The manifest registers one representative ID per group. Selecting a logical `caseId` or filter runs its whole group and every associated oracle.                                                                                                                                         |
| Browser layers             | HTML/CSS stays on Source Vite 4174. JS/TS/React keep their current built chunks on preview 4173. Tailwind and all specialist Worker, cancellation, recovery, security and state reuse tests stay unchanged.                                                                              |

At source `1764c6e98c5522fe66800c05e394e62d09aa37a3`, the four audited courses contain 1,174 logical cases in 1,071 execution groups (102 groups share input; 103 repeated executions). The count is an observed inventory, not a success criterion or a fixed assertion for future course changes. All logical contracts must continue to pass. New release evidence must be collected for a changed candidate; earlier release receipts are not reused.

The independent candidate evidence includes an exact map for all logical targets, before/after browser observations for a stated subset, and deliberately corrupted statuses, diagnostic codes, failed rules and stale-evidence acceptance. Timing applies only to the measured subset and environment; the full manifest suite has not been benchmarked by this change.

The main-derived CLI shadow regression remains alongside two synthetic, real-compiler cases. It continues to distinguish a published Tailwind course's bounded receipt from legacy shadow records. Draft setup shares delivery and expected metadata only after compiling a private copy normalized to draft; each fixture's source tree must match, and the checker still recompiles and verifies all bindings. These tests do not authorize publication. Earlier candidate observations and timings do not qualify this integration source; it requires its own focused checks and CI.
